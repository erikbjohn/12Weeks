Bottom line

The spec's shape is right — protocol as first-class data, coach awareness, meal rail, dual-line recomp goal. But as written it is not safely implementable. Three parts would corrupt data or fail silently in production, and six more would produce wrong behavior or leave implementers guessing. Everything below was reproduced by an independent verifier reading the real code; nothing here is speculative.

Blockers — would corrupt data or break silently

1. The block 2→3 transition would corrupt your training history

The spec says: re-stamp block-2 weeks 1–7 with week += 12 → weeks 13–19, "same playbook as last time." But block-1 history already lives at weeks 13–24 from the last transition. The += 12 rams block-2 into block-1's rows:

  • Tables with unique constraints (set_log, run_log — you ran every day of both blocks, so every slot collides — day_completion, weekly_checkin…) abort mid-migration.
  • Plan tables without constraints silently merge two blocks under the same week numbers.
  • Result: a half-restamped database. And the rollback ("week −= 12 on the 22 tables") is then unexecutable — there is no block column, so merged rows are indistinguishable; the unscoped −= 12 would also drag block-1 into weeks 1–12 and decrement coach_memory, which was never shifted.

The "same playbook" was only safe last time because weeks 13–24 were empty. The spec never re-checks that precondition.

Fix: cascade oldest-first, all inside one DB transaction: block-1 weeks 13–24 → 25–36 first, then block-2 → 13–18. Rollback becomes the exact scoped inverse, newest-first. Record per-week row histograms (not raw counts — counts don't change under an UPDATE, so they can't detect a botched re-stamp).

2. Today is day 0 of both blocks — today's data gets filed as ancient history

2026-08-10 is day 0 of block-2 week 7 and day 0 of block-3 week 1. Anything already logged today — your Garmin morning run auto-pulls into run_log — carries week=7 and would be shipped off as "week 19" history. Block-3 Monday then permanently shows no run (Garmin sync won't re-import it; it's idempotent by activity id), and the spec's own verification step "today = not_started" would pass while lying. There is also a live-write race between the re-stamp step and the AppState update: the app still computes "week 7" in between and can write orphan rows that resurface inside block-3's real week 7 in late September.

Fix: re-stamp only the completed weeks 1–6; in the same transaction, re-home today's week-7 rows to block-3 week 1 day 0; set AppState (start_date, current_week) in that same atomic commit; then run one forced Garmin sync and verify today's run sits on block-3's card.

3. Every taken 10 pm Tesamorelin dose would read "missed"

The repo stores datetimes in UTC. 22:00 Pacific = 05:00 UTC the next day. The spec's "a check-off only counts for its own date" gate, implemented naively (the codebase default), fails for all 28 Tesamorelin doses from Oct 5 on: nightly false "missed" flags, permanently wrong adherence % in the coach's context. And §2 gives no way at all to check off yesterday's dose the next morning. Bonus trap: DST ends 02:00 on Sun Nov 1 — the final protocol day, which itself has a 22:00 dose.

Fix: the dose row's own date column is the sole authority for which day a dose counts toward; taken_at (UTC) is audit trail only. Write-gate check-offs to user-local today/yesterday. Make the "missed: X" line tappable ("mark taken", capped at 1 day back). Test 22:05 local check-off, next-morning retro check-off, and the Nov 1 DST night explicitly.

Majors — wrong behavior, or two implementers build different apps

4. "Block goal = recomp" would silently kill the entire cut-coaching machinery

cut_status returns None unless goal_type == "cut". Setting the goal to "recomp" (a valid value) disarms: rule 21 (coach runs the cut), the gluten/water guard, the pace judgment against the curve, deficit calorie math (recomp = flat TDEE−100), and coach-prescribed fast days (silently remapped to rest days). That is a literal repeat of the block-1 failure — coach goes scale-silent.

Fix: goal_type stays "cut", target 195. "Recomp" is the block's framing, expressed through the new lift-decline detector (#7) and the waist signal. Add a served-state assertion that cut_status is non-null on day 1 — it fails loudly if anyone ever writes "recomp".

5. The weight curve has ~7 consumers; the spec named 2 — and two live endpoints would destroy it

Served today: a literal straight-line linear_plan on the dashboard, an on_pace badge judged linearly, cut_status's own linear regression, weekly_report judging against stored weight_projection, and a client-side curve computed in JavaScript. Worse: POST /api/goal/recalibrate and the admin regenerate-projection endpoint overwrite the stored projection with a linear/calorie-model curve — one authenticated call silently destroys the piecewise curve (and recalibrate tightens calories from raw, non-de-spiked weight — bypassing the gluten guard).

Fix: one canonical curve(date) function + one tolerance constant in goal_engine; piecewise targets stored once in TrainingGoal.weight_projection; every consumer enumerated and switched; /api/goal/recalibrate retired (it has zero client callers and weekly generation already recalibrates through the de-spiked path); admin regenerate rewritten; client-side curve computation removed.

6. The curve math doesn't land on 195

2×1.25 + 4×2.0 + 6×2.5 = 25.5 lb → 194.5, while the spec's headline says 195. Also unpinned: the anchor (hardcoded 220 vs your actual day-0 weigh-in — the known anchor-drift bug class), daily interpolation vs weekly steps, boundary-day semantics, and what counts as an "escalation" (the Sep 10 jump from 3 mg weekly to 3 mg twice-weekly doubles weekly exposure but is neither a curve boundary nor a defined escalation).

Fix: weeks 1–2 @ 1.25, weeks 3–6 @ 2.0, weeks 7–11 @ 2.5, week 12 @ 2.0 → exactly 25.0 lb, lands on 195.0, and the softer final week matches the week-12 deload. Publish the 12-row weekly target table in the spec as the single authority. Anchor = day-0 weigh-in (220 as seed), endpoint-preserving re-anchor exactly once. "Escalation" = any scheduled increase in weekly mg exposure, derived from the imported dose rows, never a hardcoded date list.

7. The recomp tripwire is advisory-only in disguise

"Sustained lift-performance decline" names no metric, window, threshold, or code artifact — it's left to LLM judgment, which the always-codify rule exists to ban.

Fix: a code-enforced detector (new lift_trend reader on SetLog via the shared history reader): flag fires when e1RM is down ≥5% on ≥2 of 5 key lifts for 2 consecutive non-deload weeks, OR weekly tonnage down ≥10% for 2 consecutive non-deload weeks. Emitted into coach context and the weekly report exactly like water_spike_suspected; the coach reacts to the computed flag, never to its own impression.

8. Import semantics lose data at the edges

Under the spec's (date, time, compound) key, a dose-time edit is a delete+insert — destroying the taken_at of an already-taken dose. "Today" is neither past nor future in the delete rule (both readings break the doctor-edits-CSV-midday case). And re-import can silently rewrite the historical record of doses already injected.

Fix: key on (date, compound) — verified unique across all 292 CSV rows, with an import guard enforcing it — so a time edit is a plain update. Import never touches any row with taken_at set, never inserts/updates/deletes past-dated rows, and reports skipped divergences explicitly instead of silently diverging.

9. Four "specified but not buildable" items

  • Meal rail: meal_generator is DB-free and dateless — the rail must live in the app.py weekly-generation callers, passed in as a window-end override. Two concrete violators found: the "none" fasting protocol ends at 9:00 pm, and a protein-supplement meal is hardcoded at 8:00 pm. Plans generated before the import would serve post-8pm dinners contradicting the protocol card → re-import must reconcile the current week's plan.
  • Missed-dose rules: if the doctor's rule says "take it late," the date-gate makes that unrecordable — dose stays "missed" forever, adherence and vial counts corrupt. Needs a per-compound machine-readable late window + a "taken late" action on the missed line.
  • Vial inventory: vials hold mg, not doses. A 4 mg retatrutide draw consumes twice a 2 mg one, so the spec's dose-count model overstates supply exactly when frequency also doubles — running you out of the compound driving the cut. Model in mg; compute run-out by walking the actual future schedule.
  • Prod verification: §6's checks (meals, protocol card, projection) aren't reachable with the existing ?email= debug endpoints. Add one allowlisted, GET-only serve-as-user admin endpoint and map every §6 check to the endpoint that proves it. Also: the checklist says "today's 4 doses" — today has 5.

Already fixed — the spec is fighting a ghost

10. The week-12 retest lock was fixed six weeks ago

§7 schedules fixing the "week-12 retest locks the whole app" bug. It was removed on 2026-06-29 (commit 71a2a93: RETEST_WEEKS = (), regression-pinned by tests/test_no_retest_gate.py). The coach-narrates-template bug was fixed the same day (3671d58). A stale memory index seeded the error; the memory has been corrected. §7 becomes a one-line served-state check (due_and_pending == false), not a work item.

Minors — real, small, all get spec edits

  • GHK-Cu cadence is wrong in the spec table: it's fixed Wed/Fri/Sun 3×/week, not "~every other day." Rule added: cadence text anywhere (coach, card) must be derived from dose rows, never from prose — so the doctor editing the CSV can't create a contradiction.
  • Garmin "watch" is a build, not a read: no coach-path code reads GarminWellness today, and live sync E2E with you is still unproven. Needs: extend the coach's Garmin block + weekly report, define empty-data behavior ("no synced data for N days" — never silence), store a pre-protocol RHR/HRV baseline so a drug-induced rise can't be absorbed by a rolling window, and verify data actually exists on day 0.
  • Gluten guard loses sensitivity under the steeper slope: at 2.5 lb/wk, a real 5–6 lb spike over a 7–10-day gap nets below the 3 lb trigger floor. Make the band slope-aware using the same curve function, and consolidate the two duplicated detector copies into one shared module.
  • Lab reminders: "AppState-adjacent config" doesn't exist. New tiny LabReminder table (label, due_date, completed_at); baseline due 2026-08-10, week-8 panel due 2026-09-28; coach mentions only while incomplete and due.
  • 10 pm dose vs the coach's after-10pm scold: rule 6 tells the coach to call out any post-10pm interaction; from Oct 5 the protocol requires a 22:00 check-off. Codified carve-out: protocol interactions within the dose window get "Dose done. Screens off." — everything else still gets the callout.
  • Deploy sequencing: all block-3 code deploys before the data ops (step 0), then a deploy freeze until week-1 generation completes — the generation job is an in-process daemon thread; a mid-flow deploy kills it half-written (the exact Planning-Display-Recovery failure).
  • Rollback completeness: rollback must also remove regenerated week-1 plan rows and imported PeptideDose/PeptideVial/LabReminder rows, snapshot and restore the full TrainingGoal row (the 195 target and curve live there, not in AppState), and park — never delete — any real block-3 training already logged.
  • Check-off toggle: un-check semantics defined (server round-trip nulls taken_at; missed line and adherence recompute at read time; vial counts are derivations, never stored counters).
  • Import user targeting: the CSV has no user column — the import endpoint takes an explicit email parameter.

Decisions locked in (flag now if you disagree)

Re-stamp scheme: cascade oldest-first (block-1 → 25–36, then block-2 → 13–18) in one transaction. Preserves "previous block = 13–24 … older blocks higher" ordering logic and keeps every reader working.
goal_type: stays "cut". Recomp lives in the lift-decline detector + waist signal, not in the goal enum.
Curve: 1.25 / 1.25 / 2.0×4 / 2.5×5 / 2.0 — sums to exactly 25.0, lands on 195.0, soft final deload week.
Import key: (date, compound) with time as an updatable field; rows with taken_at set are immutable to import.
/api/goal/recalibrate: retired (orphan endpoint, no client callers, bypasses the gluten guard, destroys the curve).
